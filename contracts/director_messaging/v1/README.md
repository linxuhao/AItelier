# Director messaging contract v1

This directory is the executable **statement** of the inter-director messaging
contract. It defines the four service actions, closed JSON envelopes, a
standalone in-memory fake, and provider-neutral conformance vectors. SQLite
persistence, HTTP/REST and MCP adapters, and State wait integration are outside
this statement artifact.

## Required surface

The v1 action names and arguments are exactly:

```text
send_director_message(sender_project_id, director_identity, request_key,
                      subject, body, target_project_id=null, broadcast=false,
                      reply_to_delivery_id=null)
list_director_messages(project_id, after=0, limit=100)
acknowledge_director_message(project_id, delivery_id, expected_version,
                             request_key)
resolve_director_message(project_id, delivery_id, expected_version, request_key)
```

The transport authenticates the caller and applies the existing State writer
gate before parsing an action body. The service and fake receive that
authenticated actor; `director_identity` is recorded provenance and never
authorization. An authorized writer may explicitly read any project inbox.

All success and error objects validate against [schema.json](schema.json).
Nested objects are closed. Errors have a stable code and the exact detail
`{"message": <code>}`. IDs are nonempty opaque UUIDv4 strings when generated by
the service. `created_at` is UTC with exactly six fractional digits and a `Z`
suffix.

Database project and delivery IDs are compared byte-for-byte after decoding to
Python strings; they are not normalized. Their 1..320 character bound is
checked with `len(unicodedata.normalize("NFC", value))`. `request_key` and
`director_identity` normalize to NFC and contain 1..320 code points. `subject`
normalizes to NFC and contains 1..200 code points. `body` normalizes to NFC and
contains 0..8000 code points. Booleans are not accepted as integers.

## Routing and state

Exactly one send mode is valid:

| Mode | `broadcast` | `target_project_id` | `reply_to_delivery_id` |
|---|---:|---|---|
| targeted | false | non-null | null |
| broadcast | true | null | null |
| reply | false | null | non-null |

Targeted self-send is `invalid_request`. An initial targeted or broadcast
message gets a new `message_id` and uses it as `thread_id`. A reply may cite a
delivery in any status, but that delivery must be in the sender project's
inbox. It targets the directly cited message's sender, inherits that message's
thread, records the cited delivery ID verbatim, and never replies to all
recipients. A delivery known only in another inbox is reported as
`unknown_delivery`.

Message fields are stored once; target belongs to each delivery. Each inbox has
a persistent integer `delivery_seq`, starting at 1 and increasing without gaps
for committed deliveries only. A delivery starts at `unread`, version 1. The
only transitions are `unread -> acknowledged -> resolved`, and each transition
increments version by one. Repeating the requested target state succeeds even
with an old expected version. `unread -> resolved` and every regression return
`invalid_transition`; a stale version on an otherwise legal edge returns
`version_conflict`.

Inbox listing is the only action that returns stored full bodies. It orders by
`delivery_seq`, treats `after` as an exclusive raw sequence, accepts limits
1..100, and returns the last returned sequence as `next_after` (or the supplied
`after` for an empty page).

## Idempotency and errors

All mutations require a request key. Its permanent scope is
`(actor, scope_project_id, full_action_name, request_key)`, where send uses the
sender project and acknowledge/resolve use `project_id`. The compared payload
contains every validated, default-expanded business input including the key,
uses NFC for the specified text fields and exact database IDs, excludes server
IDs and timestamps, and is sorted-key compact UTF-8 JSON.

Only a committed success creates a dedupe record. Its first response has
`replayed=false`; the same key and payload later returns the recorded business
result with `replayed=true`. A different payload returns
`idempotency_conflict`. A first already-at-target acknowledge/resolve is a
successful mutation for dedupe purposes.

Processing order is transport writer gate, service input validation, dedupe,
project lookup, target/reply/broadcast resolution, already-target handling,
invalid-edge handling, CAS, then atomic commit. Errors write nothing. Allowed
codes are `invalid_request`, `unauthorized`, `unknown_project`,
`unknown_delivery`, `idempotency_conflict`, `invalid_transition`,
`version_conflict`, `recipient_limit`, and `no_recipients`.

## Broadcast and event obligations

A SQLite provider later binds this contract using `BEGIN IMMEDIATE`. In one
transaction it snapshots every row of `state_projects`, excludes the sender,
sorts by project ID, and allocates each inbox's next sequence in that order.
There is no archive/delete exception in v1. Zero recipients returns
`no_recipients`; more than 200 returns `recipient_limit`; both leave no message,
delivery, event, sequence gap, or dedupe record. Every message-recipient pair is
unique. Message, deliveries, per-inbox sequences, events, and dedupe success
commit together. SQLite busy handling remains the database retry policy and is
not a director-messaging domain error.

Every committed delivery creates one actionable State event in the target
project in the same transaction. It has `event_type=director_message_received`,
`node_key=null`, and exactly this payload:

```json
{"message_id":"...","thread_id":"...","delivery_id":"...","summary":"..."}
```

The summary is computed once from normalized text as
`core.state_driver_notes._redact(subject + "\n" + body)[:320]` and persisted;
later redactor changes never rewrite it. The fake, SQLite provider, and event
tests use that same function.

State wait scans a fixed high watermark over `after < seq <= high`. Director
message events are universal project-level matches: they bypass node, attempt,
and filter-mode filters and remain eligible for both actionable-only values.
They share normal event ordering and the 1..500 limit. If matches exceed the
limit, `next_after` is the last returned sequence; otherwise it is
`max(input_after, high)`, including an empty page. Only the delivery target is
notified. List produces no event, and acknowledge/resolve produce no
`director_message_received` event.

The in-memory fake deliberately does not implement wait or process-restart
durability. It supports a fresh reset for conformance isolation. The later
SQLite provider must preserve IDs, sequences, versions, dedupe records, and
event cursors across restart.

## Shared verification and neutral guidance

[vectors.json](vectors.json) is provider-neutral input to the runner in
[conformance.py](conformance.py). The exact same file is run against the fake
now and the SQLite provider later. MCP gets adapter-specific tests for the same
closed envelopes and errors. The schema and vectors are versioned together;
changing observable behavior requires a new contract version.

Any later director guide or prompt describing this protocol must be
**agent-neutral**. Codex, Claude, a workflow, and an external harness may appear
only as transport examples. None is the protocol owner, a required actor type,
or an authorization source.
